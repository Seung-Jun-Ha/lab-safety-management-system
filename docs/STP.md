# 연구실 안전관리 시스템 시험 계획서 (STP/STD)

- 대상 브랜치: `kimminho`
- 기준 커밋: `651a61d` (`feat: implement waste management use case`)
- 작성 범위: 김민호 브랜치에 구현된 폐기물 관리 기능 기준
- 주요 대상 API:
  - `POST /api/waste/register`: 폐기물 정보 등록
  - `GET /api/waste/search`: 폐기물 배출 이력 조회

## 4. 단위 시험 계획 및 설계 (STP + STD 포함)

### 4.1 시험 대상

| 구분 | 시험 대상 | 주요 기능 |
| --- | --- | --- |
| Service | `WasteManagementService` | 폐기물 등록 요청 검증, 폐기물 타입 매핑, 폐기물 ID 생성, 저장, 알림 로그 생성 |
| Service | `WasteQueryService` | 연구실 ID와 폐기물 타입 ID 기준 폐기물 이력 조회 |
| Controller | `WasteManagementController` | 폐기물 등록 API 요청/응답 처리, HTTP 201 응답 반환 |
| Controller | `WasteQueryController` | 폐기물 조회 API 요청 파라미터 바인딩, HTTP 200 응답 반환 |
| Repository | `FakeWasteRepository` | 폐기물 정보 저장 및 조건 검색 |
| Validation | `WasteInfoRegisterDto`, `ApiExceptionHandler` | 필수값, 양수, 과거/현재 날짜 검증 및 400 오류 응답 |
| Logging | `AlertLogService` | 폐기물 등록 완료 알림 로그 생성 |

### 4.2 단위 시험 방법 및 검증 기준

단위 시험은 JUnit 5, AssertJ, Mockito, Spring MockMvc를 사용한다. 서비스 계층은 `FakeWasteRepository`와 `AlertLogService`를 직접 주입하여 비즈니스 로직을 검증하고, 컨트롤러 계층은 `@WebMvcTest`와 MockMvc로 HTTP 요청/응답을 검증한다.

검증 기준은 다음과 같다.

- 정상 입력 시 폐기물 정보가 저장되고 응답 DTO에 `wasteId`, `typeId`, `typeName`, `labId`, `quantity`, `unit`, `generatedDate`가 올바르게 포함된다.
- 등록 성공 시 알림 로그가 1건 생성되고 메시지와 하위 시스템 값이 기대값과 일치한다.
- 필수값 누락, 알 수 없는 폐기물 타입, 0 이하 수량, 미래 발생일 입력은 실패해야 한다.
- API 요청 성공 시 등록은 201 Created, 조회는 200 OK를 반환해야 한다.
- API 요청 실패 시 400 Bad Request를 반환하고, 비즈니스 예외는 오류 메시지를 포함해야 한다.
- 조회 조건과 일치하는 데이터만 반환하며, 조건과 일치하는 데이터가 없으면 빈 목록을 반환해야 한다.

### 4.3 단위 시험 수행 절차

1. Java 17과 Maven이 설치된 환경에서 `kimminho` 브랜치를 체크아웃한다.
2. 프로젝트 루트에서 `mvn test`를 실행한다.
3. 필요 시 다음 명령으로 대상 테스트를 개별 실행한다.

```bash
mvn -Dtest=WasteManagementServiceTest test
mvn -Dtest=WasteManagementControllerTest test
mvn -Dtest=WasteQueryControllerTest test
```

4. Maven Surefire 결과에서 실패(`Failures`)와 오류(`Errors`)가 0인지 확인한다.
5. 실패한 테스트가 있으면 실패 입력값, 기대 결과, 실제 결과를 비교하여 원인을 기록한다.

### 4.4 단위 시험 합격 기준

- 전체 단위 시험 실행 결과가 성공이어야 한다.
- 테스트별 기대 상태 코드, 응답 필드, 예외 타입, 예외 메시지, 저장 결과가 모두 일치해야 한다.
- 폐기물 등록 성공 후 알림 로그 생성 여부가 확인되어야 한다.
- 실패 케이스가 정상 케이스처럼 저장되거나 2xx 응답을 반환하지 않아야 한다.
- 테스트 실행 중 Spring 컨텍스트 로딩 오류나 직렬화/역직렬화 오류가 없어야 한다.

## 5. 통합 시험 계획

### 5.1 시험 대상

| 통합 대상 | 연결 모듈 |
| --- | --- |
| 폐기물 등록 흐름 | `WasteManagementController` -> `WasteManagementService` -> `WasteType` -> `WasteRepository` -> `AlertLogService` |
| 폐기물 조회 흐름 | `WasteQueryController` -> `WasteQueryService` -> `WasteRepository` |
| 오류 처리 흐름 | Controller Validation -> `ApiExceptionHandler` -> HTTP 400 응답 |
| 애플리케이션 실행 환경 | Spring Boot 3.3.5, Java 17, H2 설정, 3000 포트 |

### 5.2 통합 시험 방법

통합 시험은 실제 Spring ApplicationContext를 로딩한 상태에서 API 단위로 수행한다. 접근법은 API 진입점부터 서비스와 저장소까지 연결을 확인하는 상향식 검증이 아니라, 사용자 요청 흐름과 동일한 컨트롤러 중심의 하향식 검증으로 수행한다.

권장 방법은 다음과 같다.

- `@SpringBootTest`와 MockMvc 또는 랜덤 포트 테스트로 전체 빈 연결 확인
- 등록 API 호출 후 조회 API로 저장 결과 확인
- 잘못된 등록 요청이 공통 예외 핸들러를 통해 400 응답으로 변환되는지 확인
- `mvn test`에 통합 테스트를 포함하여 반복 실행 가능하게 구성

### 5.3 통합 시험 검증 기준

- Spring Boot 애플리케이션 컨텍스트가 정상 로딩되어야 한다.
- 등록 API 성공 응답의 데이터가 조회 API 결과에 반영되어야 한다.
- 컨트롤러, 서비스, 저장소, DTO 변환 간 필드 누락이나 타입 불일치가 없어야 한다.
- 검증 실패와 비즈니스 예외가 모두 400 Bad Request로 일관되게 반환되어야 한다.
- 테스트 간 데이터가 서로 영향을 주지 않도록 테스트 데이터 초기화 또는 독립 실행이 보장되어야 한다.

### 5.4 통합 시험 수행 절차

1. `kimminho` 브랜치에서 `mvn test`를 실행하여 기존 단위/API 슬라이스 테스트가 성공하는지 확인한다.
2. 전체 Spring Context 기반 통합 테스트를 추가하거나 실행한다.
3. 애플리케이션을 실행한다.

```bash
mvn spring-boot:run
```

4. 정상 등록 요청을 보낸다.

```bash
curl -X POST http://127.0.0.1:3000/api/waste/register \
  -H "Content-Type: application/json" \
  -d '{"typeId":"W01","labId":"LAB001","quantity":12.5,"unit":"kg","generatedDate":"2026-06-18"}'
```

5. 조회 요청으로 등록 데이터가 반환되는지 확인한다.

```bash
curl "http://127.0.0.1:3000/api/waste/search?labId=LAB001&typeId=W01"
```

6. 미래 날짜, 필수값 누락, 알 수 없는 타입 ID 요청이 400 응답을 반환하는지 확인한다.

### 5.5 통합 시험 합격 기준

- 등록부터 조회까지의 주요 흐름이 API 기준으로 성공해야 한다.
- 오류 입력은 저장되지 않고 400 응답으로 처리되어야 한다.
- 통합 시험 실행 결과 실패와 오류가 0이어야 한다.
- 수동 API 확인 시 JSON 응답 구조가 단위 시험 기대 결과와 일치해야 한다.

## 6. 시스템 시험 계획

### 6.1 시험 대상

현재 브랜치에서 시스템 시험 대상이 되는 비기능적 요구사항은 다음과 같다.

| 구분 | 시험 대상 |
| --- | --- |
| 실행 안정성 | Java 17 환경에서 Spring Boot 애플리케이션이 3000 포트로 정상 기동되는지 확인 |
| 성능 | 폐기물 등록/조회 API가 일반 사용량에서 허용 시간 안에 응답하는지 확인 |
| 스트레스 | 연속 등록/조회 요청 중 5xx 오류나 애플리케이션 중단이 발생하지 않는지 확인 |
| 보안 | 잘못된 입력값이 서버 오류나 스택 트레이스 노출 없이 400 응답으로 처리되는지 확인 |
| 데이터 정합성 | 폐기물 ID 중복, 미래 날짜 저장, 0 이하 수량 저장이 발생하지 않는지 확인 |
| 호환성 | README 기준 Java 17, Maven 3.6 이상 환경에서 빌드와 실행이 가능한지 확인 |

별도 성능 수치가 요구사항으로 제시되어 있지 않으므로, 아래 기준은 초기 검증 기준으로 둔다.

### 6.2 시스템 시험 방법

- 성능 시험: k6, JMeter, ApacheBench 중 하나로 등록/조회 API에 반복 요청을 보내 평균 응답 시간과 실패율을 측정한다.
- 스트레스 시험: 동시 사용자 수를 단계적으로 증가시키며 5xx 오류율, JVM 메모리 사용량, 애플리케이션 중단 여부를 확인한다.
- 보안 시험: 필수값 누락, 잘못된 타입 ID, 음수 수량, 미래 날짜, 잘못된 JSON 형식 요청을 보내 오류 응답을 확인한다.
- 실행 시험: `mvn -DskipTests package` 후 생성된 JAR를 실행하고 포트 바인딩과 API 응답을 확인한다.

### 6.3 시스템 시험 검증 기준

- 애플리케이션은 30초 이내에 기동되어야 한다.
- 정상 부하 기준 등록/조회 API 평균 응답 시간은 1초 이내여야 한다.
- 정상 부하 기준 API 실패율은 1% 미만이어야 한다.
- 스트레스 시험 중 애플리케이션 프로세스가 비정상 종료되지 않아야 한다.
- 잘못된 입력으로 인해 500 Internal Server Error나 스택 트레이스 응답이 발생하지 않아야 한다.
- 패키징과 실행이 README 절차와 일치해야 한다.

### 6.4 시스템 시험 수행 절차

1. Java와 Maven 버전을 확인한다.
2. `mvn clean test`로 테스트를 실행한다.
3. `mvn -DskipTests package`로 실행 파일을 생성한다.
4. `java -jar target/lab-safety-management-system-0.0.1-SNAPSHOT.jar`로 애플리케이션을 실행한다.
5. 정상 등록/조회 API를 호출하여 기본 동작을 확인한다.
6. 성능 도구로 등록/조회 API에 반복 요청을 수행하고 응답 시간과 실패율을 기록한다.
7. 잘못된 입력 요청을 수행하여 보안 및 오류 처리 결과를 확인한다.
8. 시험 결과를 정리하고 기준 미달 항목은 결함으로 등록한다.

### 6.5 시스템 시험 합격 기준

- 빌드, 테스트, 패키징, 실행 절차가 모두 성공해야 한다.
- 6.3의 성능, 안정성, 보안 기준을 모두 만족해야 한다.
- 치명도 높음 이상의 결함이 남아 있지 않아야 한다.
- 남은 결함이 있는 경우 우회 방법과 영향 범위가 문서화되어야 한다.

| AT-SYS-002 | 잘못된 요청이 발생해도 사용자가 이해 가능한 실패 응답을 제공하고 서버가 중단되지 않아야 한다. |

### 7.2 인수 시험 방법

인수 시험은 알파 테스트와 베타 테스트로 나누어 수행한다.

- 알파 테스트: 개발팀 또는 내부 검토자가 API 기준으로 폐기물 등록/조회 시나리오를 수행한다.
- 베타 테스트: 교수자, 조교, 팀 내 요구사항 검토자가 실제 업무 흐름에 맞춰 등록/조회 결과를 확인한다.
- 현재 브랜치의 폐기물 기능은 REST API 기준으로 구현되어 있으므로, 화면 기반 인수 시험은 UI 연결 상태가 확인된 뒤 별도 수행한다.

### 7.3 인수 시험 검증 기준

- 고객 요구사항 항목별로 성공 또는 실패를 명확히 판정할 수 있어야 한다.
- 정상 폐기물 등록 후 조회 결과에서 동일 데이터가 확인되어야 한다.
- 잘못된 입력은 등록되지 않아야 하며 실패 응답이 반환되어야 한다.
- 인수 시험 중 발견된 결함은 재현 절차, 입력값, 기대 결과, 실제 결과가 기록되어야 한다.
- 필수 요구사항에 대한 치명도 높음 결함이 없어야 한다.

### 7.4 인수 시험 수행 절차

1. 인수 시험 참여자와 시험 범위를 확정한다.
2. `kimminho` 브랜치 기준 애플리케이션을 빌드하고 실행한다.
3. 폐기물 등록 정상 시나리오를 수행한다.
4. 폐기물 조회 정상 시나리오를 수행한다.
5. 미래 날짜, 필수값 누락, 잘못된 타입 ID 입력 시나리오를 수행한다.
6. 각 요구사항의 성공 여부를 인수 시험 기록표에 표시한다.
7. 발견된 결함을 수정 대상, 보류 대상, 요구사항 변경 대상으로 분류한다.
8. 고객 또는 검토자의 최종 승인 여부를 기록한다.

### 7.5 인수 시험 합격 기준

- 7.1의 고객 요구사항이 모두 충족되어야 한다.
- 필수 업무 흐름인 폐기물 등록과 조회가 정상 수행되어야 한다.
- 잘못된 입력이 시스템에 저장되지 않아야 한다.
- 인수 시험 참여자가 치명도 높음 결함 없이 승인해야 한다.
- 보류 결함이 있는 경우 영향 범위와 처리 계획이 합의되어야 한다.
